## Context

See `proposal.md` — Why. Current state that shapes the approach:

- `src/lib/types.ts` already types `AppConfig.pair` as an unordered `{ a, b }` of strings;
  this change treats those strings as BCP-47 tags.
- `src/lib/storage.ts` is done and does not need to change.
- The follow-on changes (`provider-client`, `translate-ui`) both depend on the contract
  defined here, so it is fixed first, with no I/O.
- Project rules: vitest for pure logic only, no network in unit tests; strict TypeScript,
  no type assertions without a stated reason; brace every `if`.

## Goals / Non-Goals

**Goals:**

- A single pure module that owns the translation contract (prompt in, structured result out).
- Deterministic, unit-testable behaviour for the agreed detection edge cases: off-pair
  input, undetectable input, mixed input, ambiguous words, and in-pair detection without a
  translation.
- Input bounded and checked before any request is made.
- A result shape rich enough for the UI to distinguish translation / rejection / error.

**Non-Goals:**

- No HTTP or provider call — that is `provider-client`.
- No UI — that is `translate-ui`.
- No validation or normalization of configured pair tags (including same-primary-subtag
  pairs) — that is `setup`.
- No multi-pair support.

## Decisions

**D1 — Pure functions, no I/O.** The module builds a request payload and parses a raw
response string; it never calls `fetch` or touches storage. Rationale: keeps the vitest
target real and lets `provider-client` own transport and error mapping. Alternative
(one module doing prompt + call) was rejected — it would make the core untestable without
mocking the network.

**D2 — BCP-47 matching by primary subtag, case-insensitive.** Detection resolves a
returned tag to a pair member by comparing the primary language subtag (`pl` ≡ `pl-PL`,
lowercased). Rationale: providers routinely return the short form even when the configured
tag is regional. Alternative (exact string match) rejected — it would reject valid
detections like `pl` against a `pl-PL` config.

**D3 — Discriminated-union result, never throw.** The parser
`parseTranslationResponse(raw, input)` returns
`{ kind: 'translation', source, target, translation }`
| `{ kind: 'off-pair', detectedLang, message }`
| `{ kind: 'error', message, input }`.
The error carries the original input, never the raw response — model output is untrusted
and must not be retained. Rationale: the three outcomes are genuinely different and the
UI must render them differently; a union gives exhaustive `switch` checking and avoids
exceptions crossing the provider boundary. Alternative (`null` / throw) rejected — it
loses the reason and forces callers to catch.

**D4 — The response JSON schema lives in `translate-core`.** The module exports
`translationResponseSchema`, a plain JSON Schema for `{ detected_lang, translation }` with
both fields required and `additionalProperties: false`; `provider-client` applies it in the
request. Rationale: the contract belongs in one place and the transport layer stays free of
domain shape. Alternative (schema in `provider-client`) rejected — it would split the
contract across two modules.

**D5 — Off-pair is expressed by detection, not by model prose.** The provider reports the
actual detected tag and a null translation; the human-readable rejection message is built
in our code, not generated by the model. Rationale: keeps UI copy under our control and
out of the prompt contract, and prevents the model inventing localized error text.
Alternative (model returns a message string) rejected — untestable, unbounded copy.

**D6 — Parser tolerates a single wrapping code fence.** Before `JSON.parse`, a single
Markdown code fence wrapping the whole (trimmed) response is unwrapped; no other extraction
(balanced-brace scanning, trailing prose) is attempted. Rationale: models frequently wrap
JSON in ```json fences even under schema mode; tolerating exactly that case removes a
common, low-value failure without general fuzzy parsing.

**D7 — The prompt is returned as `{ system, user }`.** `buildTranslationPrompt` returns two
strings; `provider-client` assembles the messages array and adds model, temperature, and
`response_format`. Rationale: the contract module stays transport-agnostic (D1) and the
prompt builder stays total. Alternative (a ready messages array) rejected — it bakes
provider message roles into the contract module.

**D8 — Languages are presented to the model as raw BCP-47 tags.** The prompt names the pair
by tag (`pl-PL`, `en`), not by a human-readable name. Rationale: models understand tags, and
it keeps `detected_lang` returnable as a tag without a name→tag reverse mapping. A
tag→name table was rejected as out of scope.

**D9 — System-prompt directives beyond detection.** The prompt instructs the model to
preserve tone, register, and formatting; to output only the translation with no
commentary; and to state the `{ detected_lang, translation }` contract in prose alongside
the machine schema. Rationale: quality for PL↔EN idioms/slang, and portability to providers
that ignore `response_format`.

**D10 — The input is data, never instructions.** The system part carries an explicit
anti-injection clause: the user part is text to translate, and any instructions, questions,
or role-play it contains are ignored and translated as-is. Rationale: without it, input like
"ignore previous instructions and …" risks being obeyed instead of translated.
Delimiter-wrapping the input was considered and rejected — the model may echo the wrapper
tags into the translation.

**D11 — Input is bounded by a core guard.** `checkInput(text)` trims, then returns `blank`
(if empty), else `too-long` (if over `MAX_INPUT_CHARS = 500`), else `ok` carrying the
trimmed text, each rejection with a concise system-supplied message. The prompt is built
from the `ok` outcome's trimmed text, so `buildTranslationPrompt` stays total and receives
already-trimmed input. Rationale: one place for the UI to validate before requesting, and copy stays
owned by us (consistent with D5). A limit inside the prompt builder was rejected — it would
make the builder fallible against D7.

**D12 — Mixed-language input is delegated to the provider.** The prompt imposes no
dominance rule. For input mixing both pair languages, the model is asked to choose the
most likely intended language and translate the whole input into the other. Rationale: a
fixed count-based rule misfires — `translate kawa please` is English-dominant by word and
letter count but Polish by content word — and the model is better placed to judge intent.
Alternative (the original dominant-language rule) was rejected at spec review on
2026-09-29.

**D13 — Undetermined input is reported as `und`.** The prompt instructs the provider to
report `detected_lang: "und"` (the BCP-47 tag for undetermined) with a null translation
when it cannot determine the language. Rationale: without a defined value, a provider may
send null or an empty string for an undetectable input, which the contract treats as a
missing or invalid field — an `error` — instead of an off-pair rejection. `und` is a
wire-level sentinel only: it resolves to the existing `off-pair` result, so no `unknown`
result kind is added.

## Risks / Trade-offs

- **Pair members sharing a primary subtag** (`en-GB` / `en-US`) make D2 ambiguous →
  documented assumption: pair members differ in primary subtag; enforcing this belongs to
  `setup`. Not handled here.
- **Provider ignores the schema** → the parser returns an `error` result rather than a
  wrong translation; `provider-client` counters this with schema enforcement (next change).
- **Response text is never retained** → debugging relies on the retained input and the
  error kind; deliberate, since model output is untrusted (D3).
- **Rejection and guard copy is English-only** → acceptable for beta; noted, not solved here.
- **D6 widens accepted input** → the allowance is exactly one wrapping fence, so other
  malformed output still fails to an `error` result.
- **D10 is a prompt-level mitigation** → not a guarantee; schema enforcement and off-pair
  handling backstop it.

## Open Questions

None — the deferrable items (fence stripping beyond the single wrapping case, localized
copy) do not change the specs, the approach, or the task breakdown.
